# KeySource: редизайн работы с подписками VlessPanel

Ветка: `feature/keysource-subscriptions` · Дата: 2026-08-09 · Статус: черновик (дизайнер + кодер)

## Идея

Сейчас подписка формируется копипастом client-inbound связок из панелей в поле вставки.
Новый флоу: новая сущность **KeySource** («источник ключа») — связка клиент@панель + инбаунд@панель, из которой извлекается vless-ключ. Под клиентом — чипсы инбаундов; клик по чипсе кладёт KeySource (зелёная чипса с именем сервера) в открытую подписку. Кнопка «Создать подписку» (активна при ≥1 чипсе) генерит файл. Синк с агрегатором — руками.

## Нейминг (утверждено)

**KeySource** — утверждено Антоном. Два типа:
- **panel-backed**: хранит panelId + clientEmail + inboundId (достаёт ключ по сети с 3X-UI)
- **manual**: хранит строку vless-ключа (для старых панелей без API и разовых ключей)

## Модель данных

```
KeySource {
  id: string (uuid)
  type: "panel" | "manual"
  // panel-backed:
  panelId: string?
  clientEmail: string?
  inboundId: int?
  // manual:
  vlessLink: string?          // строка ключа
  // общее:
  label: string?              // null = авто "{remark инбаунда}-{email}" / из #label ссылки
  cachedKey: { link, fetchedAt }?   // кеш для отображения, НЕ истина
  lastTest: { status, at }?         // результат теста демоном (test-single)
  createdAt, updatedAt
  status: derived             // ok | expired | missing | panel_unreachable
}

SubKey { id, link, keySourceId? }    // keySourceId=null → manual/legacy
Subscription { id, name, status: "draft"|"active", keys: [SubKey], updatedAt }
```

Принципы:
- Панельный KeySource хранит **ссылку**, не ключ. Ключ извлекается из 3X-UI при генерации (свежий) и кешируется для отображения.
- Удаление KeySource, используемого в подписке → SubKey превращается в manual (сохраняется последний известный link) — ничего не теряется.
- Дубль (одинаковый panelId+email+inboundId) при создании — дедуп.
- Хранилище: расширить текущий JSON-сторадж (/data). При 28 подписках и ~30 KeySource полноценная БД — оверхед.

## UI-спецификация (по ответам Антона)

- **Чипса KeySource**: одна строка, выравнивание слева. Слева — надпись (имя сервера + инбаунд remark + email; для manual — label/краткое имя). Справа — статус и доступная инфа: трафик (если панель отдаёт), дата окончания, результат теста демоном.
- **Жёлтый треугольник с «!»** на чипсе = сигнал «что-то не так, ключ извлечён не будет / не работает». Для статуса «закончился» (expired) — треугольник + справа статус «закончился».
- **Статус подписки**: «черновик» | «включен» — показывать справа от подписки.
- **Manual-чипса**: серый цвет; справа нет трафика и enabled, но результат теста демоном — можно. В файл записывается при нажатии «Создать».
- **Кнопка копирования ключа в буфер** на чипсе (для ручной проверки на компе через Hiddify). Полные vless-ссылки в UI НЕ показывать — только надписи.
- **Кнопка «Создать подписку»**: активна при ≥1 чипсе. После создания — «Перегенерировать» (обновить ключи из KeySource, не трогая manual).
- **Тест подписки после создания**: кнопка теста (POST /subscriptions/:id/test — уже есть) — обязательный шаг перед релизом ключей.
- **Статус синка**: бейдж «изменено — требуется синк с агрегатором» (панель не знает факта синка — упрощение: бейдж виден после изменений, сбрасывается вручную).
- **Таймаут на операции с API 3X-UI: 10 секунд.**

## Кейсы и статусы KeySource

| Статус | Когда | Извлечение при генерации | UI |
|---|---|---|---|
| ok | панель отдаёт ключ, клиент активен, срок не истёк | включается | зелёная чипса |
| expired | expiryTime на панели истёк | **открытый вопрос**: рекомендую НЕ включать + отчёт | треугольник + «закончился» |
| missing | клиент/инбаунд удалён на панели | пропуск + отчёт | треугольник |
| panel_unreachable | таймаут/недоступна панель | пропуск + отчёт | треугольник |
| manual | ручной ключ | включается всегда | серая чипса |

## Открытые вопросы / противоречия (ревью 09.08)

1. **Треугольник vs expired**: «ключ извлечён не будет» — но expired ключ ИЗВЛЕКАЕТСЯ (просто не работает). Поведение при генерации для expired — решить (рекомендация: не включать + отчёт).
2. **Drag&drop порядка чипс** — не отвечено. Рекомендация: не в первой итерации, порядок = порядок добавления.
3. **Имя подписки-черновика** — когда вводится? Рекомендация: модалка «+ Новая подписка» сразу с именем (проверка дублей).
4. **Трафик на чипсе**: источник — 3X-UI clientStats (up/down). Нужен новый эндпоинт VlessPanel; старые панели могут не отдавать → «нет данных». Уточнить, у каких панелей брать.
5. **Результат теста демона на чипсе**: демон тестирует подписки (url) и отдельные ключи (/test-single). Предложение: кнопка «тест» на чипсе через /test-single + кеш результата (lastTest). Либо агрегация из прогонов подписки. Решить.
6. **Статус синка**: панель не знает факта синка — подтвердить упрощение (бейдж + ручной сброс).
7. **Удаление KeySource в подписках**: превращать в manual (рекомендация) — подтвердить.
8. **«Чипса одна строка» vs много данных справа** — на узких экранах не влезет; дизайнеру: обрезка (ellipsis) + тултип со всей инфой.

## Таски дизайнеру

1. Двухпанельный экран «Подписки»: слева панели → клиенты → чипсы инбаундов; справа выбранная подписка (чипсы KeySource + manual, статус «черновик|включен», кнопки).
2. Компонент «чипса KeySource»: одна строка, имя сервера + remark инбаунда + email, оттенок зелёного; статус-точка; жёлтый треугольник «!»; справа — статус/трафик/expiry/результат теста; кнопка копирования ключа; крестик удаления; тултип с деталями.
3. Компонент «manual-чипса» (серый): без трафика/enabled, с тестом демона.
4. Состояния кнопки «Создать подписку» (disabled/loading/success/error + отчёт о частичном успехе) и «Перегенерировать».
5. Модалка «+ Новая подписка» (имя, проверка дублей).
6. Пустые состояния: нет панелей/клиентов, клиент без инбаундов, подписка без чипс.
7. Loading-состояния запросов к панелям (таймаут 10с → понятная ошибка) + тосты.
8. Бейдж «изменено — требуется синк».
9. Обработка переполнения строки чипсы (ellipsis/тултип).
10. Адаптив: не ломать мобильную версию.

## Таски кодеру

Бэкенд:
1. Модель KeySource (panel/manual) + миграция JSON-хранилища; дедуп по триплету.
2. API:
   - POST /api/key-sources {type, panelId?, clientEmail?, inboundId?, vlessLink?, label?}
   - GET /api/key-sources (со статусами, кешами, lastTest)
   - DELETE /api/key-sources/:id (подписки: SubKey → manual с последним link)
   - GET /api/key-sources/:id/key (свежий из панели, кеш, force refresh)
   - GET /api/key-sources/:id/test (test-single через демон + запись lastTest)
   - GET /api/key-sources/:id/traffic (up/down из clientStats панели)
3. SubKey.keySourceId nullable; подписка: status draft|active.
4. Генерация: POST /api/subscriptions {name, keySourceIds[]} — свежие ключи из панелей, пропуск битых + отчёт; PUT — перегенерация (свежие из KeySource, manual не трогаем); кнопка «Создать» для draft.
5. Таймаут 10с на операции с 3X-UI; понятные ошибки; частичный успех.
6. Кеш ключей TTL + force-refresh; lastTest кеш.

Фронтенд:
7. Двухпанельный экран по дизайну; группировка клиентов по панелям (GET /api/panels/:id/inbounds + clients).
8. Клик по чипсе инбаунда → добавление KeySource в активную подписку (нет активной → предложить создать).
9. Кнопки «Создать подписку»/«Перегенерировать», отчёт после генерации.
10. Копирование ключа в буфер; статусы чипс; тосты; пустые состояния; бейдж синка.

Тестирование (ручной сценарий): создание из KeySource → файл; перегенерация; недоступная панель → отчёт; legacy-подписка не ломается; expired → треугольник; manual-ключи; копирование; тест подписки после создания.
